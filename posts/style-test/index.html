A large language model generates text one token at a time. Each step runs the whole network on one new token per request, so the GPU must read every weight from memory to do only a little arithmetic. This post shows why that makes decoding limited by memory bandwidth rather than compute, and why batching and KV-cache management matter so much to inference engines such as vLLM [1].

Attention and the KV cache

Each Transformer layer computes scaled dot-product attention [2]:

\[ \mathrm{Attention}(Q, K, V) = \mathrm{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right) V. \tag{1}\]

During decoding, the keys and values of earlier tokens never change, so engines store them in a KV cache instead of recomputing them. For a model with \(L\) layers and \(n_{kv}\) key-value heads of dimension \(d_h\), serving a batch of \(b\) sequences of length \(s\) with \(p\) bytes per element, the cache needs

\[ M_{\mathrm{KV}} = 2 \cdot L \cdot n_{kv} \cdot d_h \cdot s \cdot b \cdot p \ \text{bytes}, \tag{2}\]

where the factor 2 counts both keys and values.1

1 Grouped-query attention [3] shares each key-value head across several query heads, which shrinks \(n_{kv}\), and the cache, by the same factor.

Take a 7B model with 32 layers and 32 heads of dimension 128 (the shape of Llama 2 7B), stored in FP16. Equation 2 gives 0.5 MiB per token, so a single 4,096-token sequence already needs 2 GiB (Listing 1, Table 1).

Why decoding is memory-bound

The arithmetic intensity \(I\) of a kernel is the number of floating-point operations it performs per byte it moves. The roofline model [4] says that on a machine with peak compute \(P\) and memory bandwidth \(B\), the kernel can reach at most

\[ \text{attainable FLOP/s} = \min(P,\; I \cdot B). \tag{3}\]

Proposition 1 (Intensity of a decode step) Multiply a weight matrix \(W \in \mathbb{R}^{m \times n}\) stored in FP16 by a batch of \(b\) activation vectors. The arithmetic intensity satisfies \(I \le b\) FLOP/byte, and \(I \approx b\) when \(b \ll \min(m, n)\).

Proof. The product takes \(2mnb\) FLOPs: one multiply and one add per weight per vector. It reads the \(mn\) weights and the \(bn\) inputs and writes the \(bm\) outputs, at 2 bytes each, so \[ I = \frac{2mnb}{2mn + 2b(m + n)} \le \frac{2mnb}{2mn} = b. \] When \(b \ll \min(m, n)\), the term \(2b(m + n)\) is small next to \(2mn\), so \(I \approx b\).

So a single request decodes at about 1 FLOP per byte. NVIDIA’s H100 SXM is specified at about 989 TFLOP/s of dense BF16 compute and 3.35 TB/s of memory bandwidth, a ratio of roughly 295 FLOP/byte.2 By Equation 3, the GPU stays bandwidth-limited until a batch holds about 295 sequences (Figure 1). That is why inference engines work so hard to batch requests together, and why the KV cache in Table 1, which competes with the batch for GPU memory, is the resource they manage most carefully.

2 This ignores reading the KV cache itself. That adds bytes at every step without adding weight FLOPs, so real decoding is even more memory-bound.
